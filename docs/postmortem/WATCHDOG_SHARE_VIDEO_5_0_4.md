# 5.0.4 워치독 종료: 영상 102장을 메인에서 구웠다

2026-08-29 · 하루에 여덟 건 · 5.0.4 · **0x8BADF00D (워치독 종료)**

> ⚠️ **이 진단은 빗나갔다.** 뒤에 리포트 하나에 심볼을 붙였더니 멈춘 자리는 영상 굽기가
> 아니라 **입력 포커스 ↔ 뷰 그래프 갱신 고리**였다.
> → `docs/postmortem/WATCHDOG_FIRST_RESPONDER_5_0_4.md`
>
> 아래에 적힌 수정(굽기를 메인 밖으로, 취소 듣기)은 그대로 유효하고 실측으로 좋아졌지만
> (메인 최대 정지 484ms → 60ms), **그 여덟 건의 원인은 아니었을 가능성이 크다.**
> 이 문서는 "정황만으로 원인을 단정하면 어떻게 되는지" 의 기록으로 남겨 둔다.

## 리포트가 말한 것

심볼 없이도 읽혔다. `RBSTerminateContext` 만으로 끝났다.

| 시각 | 기기 | 이벤트 | 가시성 | 허용 | 앱 CPU |
| --- | --- | --- | --- | --- | --- |
| 16:20 | iPhone18,2 | scene-update | Background | 10.00s | 9.702s |
| 14:45 | iPhone14,2 | process-exit | Foreground | 5.00s | 4.713s |
| 09:11 | iPhone16,2 | process-exit | Foreground | 5.00s | 4.766s |
| 08:13 | iPhone17,2 | scene-update | Background | 10.00s | 9.027s |
| 05:47 | iPhone18,2 | process-exit | Foreground | 5.00s | 4.810s |
| 03:52 | iPhone17,2 | scene-update | Background | 10.00s | 9.431s |
| 02:36 | iPhone14,3 | scene-update | Background | 10.00s | 9.312s |
| 02:04 | iPhone14,2 | process-exit | Background | 5.00s | 4.778s |

여기서 두 가지가 곧바로 나온다.

**하나. 기다린 게 아니라 태웠다.** 앱 CPU 가 허용 시간과 거의 같다(10초에 9.7초,
5초에 4.8초). 어딘가에서 막혀 있었다면 CPU 는 0에 가까웠을 것이다. 코어 하나를
끝까지 문 채로 죽었다. 여덟 건 모두 16% 로 똑같은데, 이건 멀티코어 전체 대비라
**코어 하나를 100% 가까이 썼다**는 뜻이다. `Thermal State: nominal` 이라 발열
때문에 느려진 것도 아니다.

**둘. 두 얼굴이지만 병은 하나다.** `scene-update` 는 "장면 갱신을 10초 안에 못
끝냈다" 이고, `Failed to terminate gracefully after 5.0s` 는 "나가라고 했는데 5초
안에 못 나갔다" 이다. 메인 스레드가 잡혀 있으면 둘 다 일어난다. 앞의 것은 그릴
차례가 안 와서, 뒤의 것은 나가라는 말을 들을 차례가 안 와서다.

한 리포트(02:04)는 같은 오프셋(`5824364`)이 스택을 따라 계속 반복된다. 한 자리를
맴돌고 있었다는 뜻이다.

## 어디였나

5.0.4 에 들어간 것 중 CPU 를 오래 쓰는 것은 하나뿐이었다.
`613f5fe feat(공유): 아낀 시간을 그려지는 것으로 바꿔 말하고...` 가 들여온
**아낀 시간 공유 영상**이다.

```swift
@MainActor                      // ← 여기
enum ShareVideoRenderer {
    static let size = CGSize(width: 1080, height: 1920)
    static let fps = 30
    static let duration = 3.4   // → 102장
```

한 장이 1080×1920 = 2.1MP 다. 102장이면 **212MP** 를 굽는데, 장마다 두 번씩 일이 붙는다.

1. `ImageRenderer(content:).uiImage` - SwiftUI 한 장을 그린다
2. `pixelBuffer(from:)` - 그 2.1MP 를 CGContext 로 픽셀 버퍼에 다시 옮긴다

`enum` 전체가 `@MainActor` 라 **둘 다 메인에서** 돌았다. 고리 안의 유일한 중단점은
`while !input.isReadyForMoreMediaData` 안의 `Task.sleep` 인데, 이건 **인코더가 밀릴 때만**
걸리는 우연한 숨구멍이다. 굽기가 스스로 메인을 놓아 주는 자리는 없다.

그리고 이 굽기는 사용자가 따로 시키는 게 아니다.

```swift
.task { await make() }   // ShareVideoSheet - 시트가 열리면 바로 굽는다
```

공유 시트를 연 사람은 전원이 이 고리에 들어간다. 하루 여덟 건이 나온 이유다.

가시성이 대개 `Background` 인 것도 맞아떨어진다. 굽는 데 몇 초가 걸리니 그동안
사람은 앱을 떠나거나 공유 시트로 넘어가고, 그 순간 시스템이 요구하는 장면 갱신을
앱이 못 해 준다.

## 재 봤다 (시뮬레이터, iPhone 17 Pro, iOS 26.2)

고치기 전후로 **메인이 한 번에 막혀 있던 최대 시간**을 쟀다. 워치독이 보는 값이 그것이다.
메인에서 5ms 마다 깨어나며 깨어나기까지 걸린 간격을 재는 방식이다.

| | 굽는 데 걸린 시간 | **메인 최대 정지** | 인코더 대기 프레임 |
| --- | --- | --- | --- |
| 고치기 전 (`@MainActor`) | 7.02 / 8.50 / 7.65초 | **484 / 419 / 582ms** | 69~82 / 102 |
| 고친 뒤 | 6.50초 | **60ms** | - |

**최대 정지가 8배 줄었다.** 취소도 이제 듣는다(예전에는 시트를 닫아도 끝까지 구웠다).
두 가지 모두 시험으로 붙잡아 뒀다.

### 그런데 이 숫자가 10초를 설명하지는 않는다

정직하게 적어 둔다. 고치기 전에도 시뮬레이터에서는 최대 정지가 0.5초 언저리였다.
0.5초로는 10초짜리 워치독이 안 터진다. **이 기계에서는 크래시 조건이 재현되지 않았다.**

이유로 짐작하는 것은 인코더 속도다. 시뮬레이터는 H.264 를 소프트웨어로 밀어서
102장 중 69~82장에서 `isReadyForMoreMediaData` 가 거짓이 됐고, 그때마다 `Task.sleep` 이
메인을 놓아 줬다. **느린 인코더가 우연히 병을 가려 준 셈이다.** 하드웨어 인코더를 쓰는
실기기는 그 조건이 거의 참이라 숨구멍이 사라지고, 정지 시간이 굽기 전체 길이 쪽으로
늘어난다는 것이 짐작이다.

그 짐작은 **확인하지 못했다.** 대기를 건너뛰어 빠른 인코더를 흉내 내 보려 했으나
AVFoundation 이 프레임을 버리며 죽어서 값을 못 얻었다. 실기기에서 같은 계측을 돌리는
것이 다음 순서다.

## 같은 병의 세 번째다

| 판 | 자리 | 생김새 | 하는 일 |
| --- | --- | --- | --- |
| 4.4.6 | `CKContainer(identifier:)` | 값 하나 만들기 | 데몬과 주고받기 |
| 5.0.1 | `UIPasteboard.general.string` | 속성 하나 읽기 | pasteboardd 와 주고받기 |
| **5.0.4** | `ShareVideoRenderer.render` | `await` 붙은 async 함수 | **메인에서 212MP 굽기** |

앞의 둘은 "가벼워 보이는데 기다린다" 였고, 이번 것은 "async 라서 안전해 보이는데
메인을 안 놓는다" 이다. **`async` 는 메인을 놓아 준다는 뜻이 아니다.**
`@MainActor` 인 채로는 `await` 를 만나기 전까지 메인을 쥐고 있고, 중단점이 없는
고리는 끝까지 쥔다.

## 고친 것

### 1. 메인에서 해야만 하는 것만 메인에 남겼다

`ShareVideoRenderer` 에서 `@MainActor` 를 뗐다. `ImageRenderer` 가 메인 액터라
`frame(...)` 하나만 `@MainActor` 로 남기고, 픽셀 버퍼로 옮기는 일과 인코더에 넣는
일은 메인 밖으로 보냈다.

효과는 두 겹이다. 메인이 하는 일이 장당 절반으로 줄고, 무엇보다 **장마다 액터를
넘나들며 메인이 풀린다.** 102번 숨 쉴 자리가 생긴 셈이라 장면 갱신이 굶지 않는다.

### 2. 취소를 듣는다

```swift
try Task.checkCancellation()
```

`.task` 는 화면이 사라질 때 취소를 걸어 주는데 고리가 그걸 안 듣고 있었다. 시트를
닫아도 안 볼 영상을 끝까지 구웠다. 닫는 순간 그만둔다. 시트 쪽에서는
`CancellationError` 를 실패로 치지 않는다(닫았는데 진동이 울리면 안 된다).

### 3. 시험 (`ClipKeyboardTests/ShareVideoMainThreadTests.swift`)

영상이 잘 나오는지가 아니라 **굽는 동안 메인이 숨을 쉬는지**를 지킨다. 메인에서
20ms 마다 뛰어 보면서, 0.4초 동안 몇 번 뛰었는지 센다.

`@MainActor` 를 도로 붙여 놓고 돌려 확인했다. 심장 박동이 멈추고 시험이 실패한다.
되돌아가면 잡힌다.

## 확정 못 한 것

**이 여덟 건의 원인이 공유 영상이라는 것은 정황이지 증명이 아니다.** 근거는 넷이다.

1. 크래시가 전부 5.0.4 인데, 영상 굽기가 5.0.4 에 들어왔다(`613f5fe`)
2. 앱 CPU 가 허용 시간과 같다 = 태우고 있었다. 5.0.4 에 들어온 것 중 CPU 를 몇 초씩
   태우는 것은 이것뿐이다
3. 시트를 열면 자동으로 굽는다. 크래시 건수가 나오려면 많은 사람이 지나야 하는데 그렇다
4. `scene-update` 와 `terminate gracefully` 두 얼굴이 모두 "메인이 잡혀 있다" 로 설명된다

반대로 **없는 것**은 앱 프레임이다. 5.0.4 아카이브가 로컬에 없어 크래시 스택의 앱
오프셋을 함수 이름으로 못 바꿨다. 그게 있으면 한 줄로 끝난다.

## 다음에 같은 것이 오면

- **`RBSTerminateContext` 를 먼저 읽는다.** 앱 CPU 가 허용 시간에 가까우면 태운
  것이고(무한 고리·무거운 계산), 0에 가까우면 기다린 것이다(I/O·IPC·락).
  심볼화는 그 다음이다. 이번엔 심볼 없이 끝났다.
- 메인 액터에서 도는 **고리**를 의심한다. 중단점 없는 고리는 길이만큼 메인을 쥔다.
- `async` 라는 이유로 안전하다고 보지 않는다. 어느 액터에서 도는지가 전부다.
