# 콜스택을 149건 통째로 날린 이야기

크래시 진단을 1년 가까이 모았는데, 모은 것 전부가 읽을 수 없는 데이터였다.

## 증상

허브에 쌓인 `CrashReport` 149건을 열어 보면 `stack` 이 **하나도 빠짐없이 정확히 4000자**였다.

```
stack 길이: min 4000 · max 4000 · 평균 4000
JSON 파싱: 149건 전부 실패
4000자 안에 들어간 프레임: 전부 13개
```

## 원인

`DiagnosticsService.stackString` 이 이랬다.

```swift
private static func stackString(_ tree: MXCallStackTree) -> String {
    let data = tree.jsonRepresentation()
    let text = String(data: data, encoding: .utf8) ?? "-"
    return String(text.prefix(maxStackLength))   // 4000
}
```

`MXCallStackTree.jsonRepresentation()` 은 **들여쓴 중첩 JSON** 이다. 프레임이 깊어질수록
들여쓰기가 길어져서, 프레임 하나가 300자 안팎을 먹는다. 4000자면 13프레임에서 끝난다.

세 가지가 한꺼번에 어긋났다.

1. **잘린 쪽이 반대였다.** 트리는 뿌리에서 잎으로 중첩된다. 앞에서 4000자를 자르면
   남는 건 `start` → `main` → 런루프, 즉 **어느 크래시에나 똑같이 있는 부분**이다.
   정작 죽은 자리인 가장 깊은 프레임은 통째로 잘려 나갔다.
2. **바이너리 이름이 한 번도 안 담겼다.** 프레임의 `binaryName` 과 `address` 는
   `subFrames` **뒤에** 오는 필드다. 첫 프레임의 `subFrames` 안으로 들어가면 다시는
   그 프레임의 끝에 도달하지 못하므로, 이름 필드는 단 한 번도 나오지 않았다.
   어느 줄이 내 코드이고 어느 줄이 UIKit 인지 가릴 수가 없었다.
3. **JSON 이 깨졌다.** 중간에서 잘려 문법이 성립하지 않으니 기계로 다시 읽을 수도 없었다.

남은 13프레임으로 지문을 만들어 묶어 보면 **크래시 142건에서 그룹이 133개** 나온다
(128개가 1건짜리). 묶이는 게 없으니 "무엇이 제일 많이 죽는가"를 물을 수가 없다.

## 고친 것

콜스택을 보내기 전에 **프레임 한 줄짜리 텍스트로 편다.** 0번이 죽은 자리다.

```
 0 ClipKeyboard +820588
 1 SwiftUI +1042364
 2 UIKitCore +558784
... 뿌리 쪽 42프레임 생략
```

- 한 줄이 30자 안팎이라 8000자에 200프레임 넘게 들어간다. 13프레임과는 자릿수가 다르다.
- 상한에 걸리면 **뿌리 쪽부터 버린다.** 죽은 자리를 지키는 쪽이 언제나 옳다.
- 이름이 붙어서 내 코드 프레임을 가려낼 수 있다.

### 깊은 스택을 위한 대비책

`JSONSerialization` 은 중첩 깊이에 한도가 있다. 프레임 하나가 사전+배열 두 겹이라
**250프레임 언저리에서 파싱 자체가 실패한다.** 그런데 무한 재귀로 죽은 스택이 정확히
그 모양으로 온다. 가장 알고 싶은 크래시에서 파서가 손을 드는 셈이다.

그래서 파싱이 실패하면 중괄호만 세는 스캐너로 넘어간다. **안쪽 프레임이 먼저 닫히므로
닫히는 순서가 곧 잎에서 뿌리 순서**라, 깊이에 상관없이 프레임을 건져 낸다.

이 스캐너는 필드가 나오는 **순서에 기대지 않는다.** 처음에는 "offset 은 앞에, binaryName 은
뒤에 나온다"는 규칙을 이용해 정규식으로 짝지었는데, 시험을 쓰다가 그 가정이 약속된 것이
아님을 알았다(JSON 객체의 키 순서는 보장되지 않는다). 순서가 바뀌면 이름과 오프셋이
서로 다른 프레임끼리 붙어 **조용히 틀린 스택**이 나온다. 깨진 데이터보다 나쁘다.

## 함께 고친 것

| 필드 | 왜 |
|---|---|
| `occurredAt` | 크래시가 **난** 시각. 레코드 생성 시각은 MetricKit 이 배달한 때라 하루까지 늦다 |
| `buildNumber` | `MXMetaData.applicationBuildVersion`. 죽은 빌드를 정확히 가리키는 유일한 값 |
| `exceptionType` · `exceptionCode` · `signal` | 종료 사유 한 줄로는 SIGSEGV 와 워치독이 안 갈린다 |

`appVersion` 은 여전히 `Bundle.main` 에서 읽는다. 그건 **지금 깔려 있는** 버전이지 죽은
버전이 아니다. MetricKit 이 하루까지 늦게 배달하므로, 그 사이 업데이트가 깔렸으면 옛 버전의
크래시가 새 버전 이름표를 달고 올라온다. `buildNumber` 와 어긋나면 이름표를 의심해야 한다.

## 시험

`ClipKeyboardTests/DiagnosticsStackTests.swift` 가 세 가지를 못 박는다.

1. 죽은 자리가 0번으로 온다 (잘려도 살아남는 쪽이 거기다)
2. 바이너리 이름이 모든 줄에 붙는다
3. 깊은 스택이 13프레임에서 끊기지 않는다 (파서가 감당 못하는 600프레임까지)

시험의 페이로드는 **글자로 직접 찍는다.** `JSONSerialization` 에 Dictionary 를 넘겨
만들면 키 순서가 뒤섞여서, `binaryName` 이 `subFrames` 뒤에 온다는 사실이 시험에서
사라진다. 그 순서가 바로 이 사고의 원인이었다.

## 남은 일

이미 올라온 149건은 되살릴 수 없다. 지우고 새로 모은다.
